# 복합 증거 기반 Incident 명세

- 작성일: 2026-08-25
- 상태: 계약·runtime 구현 완료. 운영 전환 승인됨(`incident_operational_handoff_approved=true`).
  오병합률·복구 실측 표본 대기
- 적용 범위: `agent.trigger.v1` → Incident Correlator → `agent.incident.v1` → Agent Invocation Queue → Dify
- 계약 원본: `docs/contracts.md` 5.8~5.9 및 `docs/contracts/agent-*.schema.json`
- 결정 근거: D-050, D-055, D-070, D-075, D-076

## 1. 목적

Metric 또는 source 신호 하나를 Incident로 간주하지 않는다. Datadog Monitor와 Chat Incident
Candidate를 검증·정규화하고, 서로 독립적인 증거가 같은 사건을 가리킬 때 revisioned Incident로
승격한다. Dify에는 검증된 최신 Incident snapshot만 전달한다.

```text
Observation/Metric
  -> source signal
  -> agent.trigger.v1 Signal Queue
  -> deterministic Incident Correlator
  -> revisioned Incident State
  -> agent.incident.v1 Invocation Queue
  -> Generic Worker
  -> Dify custom_alert_json
```

LLM은 Incident 생성, taxonomy 분류, 병합 여부를 결정하지 않는다.

## 2. 불변조건

1. Signal Queue에는 `agent.trigger.v1`만 들어간다.
2. Incident State와 Invocation Queue의 snapshot은 `agent.incident.v1`이어야 한다.
3. source 원문이나 alert 제목을 분석해 taxonomy를 추측하지 않는다.
4. Datadog Monitor ID와 Chat surface의 명시 mapping만 taxonomy 입력으로 사용한다.
5. 같은 사건은 `incident_id`를 유지하고 material change에만 revision을 증가시킨다.
6. `PROVISIONAL`과 `AMBIGUOUS`는 State에 저장하지만 Invocation Queue에는 보내지 않는다.
7. `primary`와 `corroborating` 역할이 모두 채워진 `VERIFIED` material revision만 Agent를 호출한다.
8. Dify 멱등 키는 `incident:<incident_id>:revision:<revision>`이다.
9. raw chat, 사용자 키, 원문 일부, 원문 hash를 Incident·Dify·로그·DLQ에 넣지 않는다.
10. 환경은 배포 environment와 exact match한다. namespace 별칭을 추측하지 않는다.

## 3. Incident taxonomy

`normalized_context.incident_family`는 다음 통제 어휘 중 하나다.

| Incident family | 대표 사용자 영향 | primary evidence 후보 | corroborating evidence 후보 | 현재 구현 상태 |
|---|---|---|---|---|
| `READ_PATH_DEGRADATION` | 상품·재고·페이지 조회 지연 또는 실패 | read-path latency/error, Chat READ_PATH Candidate | cache/fallback, pod별 latency | 계약·READ_PATH mapping 구현 |
| `CHECKOUT_ORDER_DEGRADATION` | 주문 생성·확정 지연/실패, 중복 위험 | order create/confirm 결과 | queue age, cancel/retry | 통제 어휘만 구현 |
| `PAYMENT_DEGRADATION` | 결제 지연 또는 실패 | payment result | provider/DB/request latency | 통제 어휘만 구현 |
| `INVENTORY_DEGRADATION` | 재고 조회 실패·fallback·불일치 | inventory result/invariant | cache hit, fallback, DB span | 통제 어휘만 구현 |
| `CHAT_DEGRADATION` | 전파 지연·발화 실패·정상 사용자 차단 | propagation latency, block rate | Chat Candidate, chat service saturation | **S1 monitor 3개 mapping 적용** |
| `PLAYBACK_DEGRADATION` | 재생 시작 실패·buffering·stall | playback telemetry | 다수 사용자 Candidate | 통제 어휘만 구현 |
| `CAPACITY_SATURATION` | 용량 고갈 임박 또는 사용자 영향 발생 | saturation과 사용자 영향의 결합 | CPU/memory/queue/pod scope | 통제 어휘만 구현 |
| `DEPLOYMENT_REGRESSION` | 신규 version에서만 지연·실패 악화 | version별 user-impact signal | deploy time, pod age | 통제 어휘만 구현 |
| `TELEMETRY_PIPELINE_FAILURE` | 서비스 상태를 신뢰성 있게 판정할 수 없음 | canary/freshness/DLQ | Adapter·Worker error | 통제 어휘만 구현 |
| `DATA_INTEGRITY_SECURITY_RISK` | 중복 주문·잘못된 차감·계약/보안 위반 | 검증된 invariant violation | 감사·업무 결과 evidence | 통제 어휘만 구현 |
| `UNKNOWN` | 분류 불가 | 없음 | 없음 | mapping 값으로 금지; ambiguity 결과 전용 |

`UNKNOWN`은 새 Monitor의 편의상 기본값이 아니다. 환경 불일치나 필수 mapping 누락처럼 안전하게
분류할 수 없는 신호를 `AMBIGUOUS`로 격리할 때만 Correlator가 생성한다.

## 4. 정규화와 correlation key

정상화된 Incident context는 다음 필드를 가진다.

| 필드 | 규칙 |
|---|---|
| `environment` | Correlator 배포 environment. Datadog `env`와 exact match |
| `incident_family` | 명시 mapping의 taxonomy 통제 어휘 |
| `symptom_family` | `LATENCY`, `AVAILABILITY`, `ERROR_RATE`, `UNKNOWN` |
| `suspected_surfaces` | 현재 계약의 `READ_PATH`, `PLAYBACK`, `CHAT`, `UNKNOWN` 집합 |
| `services` | source mapping으로 정한 service 집합 |
| `broadcast_ids` | 방송 식별자 집합. Chat Candidate 뿐 아니라 Datadog evidence 의 `broadcast_id` 도 채택한다(D-086). correlation key 에는 들어가지 않고 context 로만 실린다 |

자동 병합 key는 다음 차원을 순서대로 결합한다.

```text
environment
  + incident_family
  + symptom_family
  + service
  + suspected_surface
```

자동 병합은 다음 조건을 모두 만족하는 OPEN Incident가 정확히 하나일 때만 허용한다.

1. environment exact match
2. incident family 일치
3. symptom family 일치
4. service와 surface 일치
5. source event time이 correlation window 안에 있음

현재 초기 Shadow correlation window는 420초다. 이는 운영 확정값이 아니라 D-073의 제한된
측정과 5분 Monitor full window에 근거한 초기값이며, 반복 측정 후 재검토해야 한다.

## 5. 상태와 lifecycle

### 5.1 Correlation 상태

| 상태 | 생성 조건 | Agent 호출 |
|---|---|---|
| `PROVISIONAL` | 일치하는 OPEN Incident가 없고 단일 source만 존재 | 금지 |
| `CORRELATED` | 유일한 OPEN Incident에 반대 source evidence가 결합 | 허용 |
| `AMBIGUOUS` | 필수 차원 누락, 환경 불일치, 병합 후보가 둘 이상 | 금지 |

### 5.2 Lifecycle

| lifecycle | 의미 | 현재 판정 |
|---|---|---|
| `OPEN` | 진행 중인 Incident | 최초 State 생성 |
| `RECOVERING` | 기존 Incident에 Datadog `Recovered` evidence가 추가됨 | 구현됨 |
| `RESOLVED` | primary·corroborating recovery와 설정된 지속 window 충족 | 구현됨; 운영 window는 측정 전 0 |

`Recovered` 한 건만으로 즉시 `RESOLVED`로 만들지 않는다. 회복 지속 window와 source별 종료
규칙은 실측 없이 정하지 않는다.

## 6. Revision과 material change

현재 revision을 증가시키는 변화:

- 최초 Incident State 생성
- 첫 cross-source evidence 추가
- Datadog recovery evidence 추가

revision을 증가시키지 않는 변화:

- 같은 source의 반복 전달
- 동일 idempotency key 재전달
- Monitor renotify와 같은 비물질적 same-source update

향후 material change로 구현해야 하는 항목:

- severity의 의미 있는 변화
- 영향 범위 확대 또는 축소
- 새로운 version 연관
- recovery 지속 조건 충족

새 revision이 authoritative State보다 오래되면 Worker는 `SUPERSEDED`로 종료한다.

### 6.1 Evidence assessment

Correlator는 각 trigger를 명시 mapping에 따라 분류하고 Incident snapshot에 다음 결과를 남긴다.

```json
{
  "evidence_assessment": {
    "primary": ["trg_..."],
    "corroborating": ["trg_..."],
    "context": [],
    "missing_required_roles": [],
    "verification_state": "VERIFIED"
  }
}
```

`verification_state`는 `INSUFFICIENT_EVIDENCE`, `VERIFIED`, `AMBIGUOUS` 중 하나다. trigger는
둘 이상의 역할에 동시에 속할 수 없고, snapshot의 `signals`에 없는 trigger ID를 참조할 수
없다. 같은 source라도 아직 비어 있는 역할을 채우면 material evidence이며, 이미 채워진 같은
역할의 반복은 revision과 Invocation을 만들지 않는다.

## 7. Invocation과 실패 격리

### 7.1 Signal claim

| 조건 | claim 상태 전이 |
|---|---|
| Invocation 불필요 | 최초부터 `NOT_REQUIRED` |
| Invocation 필요 | `PENDING` → Queue 전송 → `EMITTED` |
| Queue 전송 실패 | `PENDING` 유지, 같은 snapshot 재전송 가능 |

`PROVISIONAL`과 `AMBIGUOUS`는 `NOT_REQUIRED`다. `CORRELATED` material revision만 `PENDING`으로
저장한 뒤 Invocation Queue로 보낸다.

### 7.2 Dify handoff

- 입력: `agent.incident.v1` 전체 snapshot의 compact JSON string
- Dify 변수: `custom_alert_json`
- 최대 길이: 30,000자
- 성공: HTTP 2xx만으로 판정하지 않고 `data.status=succeeded` 확인
- timeout: Dify 도달 여부가 불명확하므로 자동 재호출 금지
- 최신 revision 확인 후 실행
- revision ledger와 Incident lock을 하나의 DynamoDB transaction으로 획득
- Incident별 실행·조치 lock은 하나만 허용

## 8. S1·S2·S3 귀속

| 시나리오 | 목표 family | 현재 가능한 evidence | 현재 상태 |
|---|---|---|---|
| S1 예정된 이벤트 중 채팅 과부하 | `CHAT_DEGRADATION` | Chat Candidate, chat rate Monitor, propagation p95 Monitor(22076983), block-rate Monitor(22076982) | Datadog Monitor는 운영 생성됨. Incident 승격은 방송별 `broadcast_id` 입력 경계와 mapping 승인 후 활성화 |
| S2 한 파드 CPU 조임과 tail latency | `CAPACITY_SATURATION` 또는 증상에 따른 degradation family | service/pod latency, pod CPU, version, pod age | `VERIFY`: pod scope evidence 계약과 분류 규칙 필요 |
| S3 사람/자동화 미확정 읽기 급증 | `READ_PATH_DEGRADATION` | Chat READ_PATH Candidate + Datadog READ_PATH Monitor | 구현된 mapping·cross-source correlation 사용 |

S3의 actor 판정은 `UNDETERMINED`를 유지한다. UA/IP diversity, interval CV, 집중도는 가설
evidence일 뿐 사람/자동화를 확정하는 값이 아니다.

## 9. Severity 원칙

Severity는 다음 입력을 사용해야 한다.

```text
severity = f(
  user_impact,
  affected_scope,
  business_criticality,
  persistence,
  integrity_or_security_risk,
  evidence_confidence
)
```

`agent.incident.v1.severity_assessment`가 통제 등급과 이전 등급, material change, 근거 trigger를
보존한다. 숫자 임계값은 Monitor가 소유하며 Correlator는 mapping의 등급만 사용한다.

높은 트래픽 자체는 severity 입력이 아니라 context다. 사용자 영향이 없는 용량 임박은 사용자
장애와 구분한다. telemetry 결측은 정상이나 0이 아니라 판단 불능으로 보존한다.

## 10. Suppression과 즉시 예외

현재 구현된 suppression:

- 단일 source Incident의 Agent 호출 금지
- ambiguity의 자동 병합·Agent 호출 금지
- 동일 signal idempotency key 중복 제거
- same-source 비물질 update의 revision·Invocation 억제
- 환경 불일치 격리
- taxonomy mapping 누락 격리

운영 측정·승인 대기:

- 짧은 spike와 지속 plateau 분리
- 큐시트/방송 phase 기반 정상 이벤트 context
- Shadow 반복 표본에 따른 production grouping/cooldown/reopen 숫자 확정
- 운영 Monitor/Webhook 연결과 Operational mode 승인

단일 강신호 예외는 `DATA_INTEGRITY_SECURITY_RISK` + `INTEGRITY_VIOLATION` + mapping allowlist +
`signal_strength=STRONG` + 유효 data quality 조합에만 열린다. 자동 조치는 계속 금지한다.

## 11. 개인정보와 안전 경계

- Chat 원문, 일부 문자열, hash, 사용자 식별자는 Incident evidence에 금지
- `raw_chat_included=false` 고정
- `analysis_mode=READ_ONLY` 고정
- `automatic_remediation_allowed=false` 고정
- `must_preserve_uncertainty=true` 고정
- `single_incident_action_lock_required=true` 고정
- payload·evidence는 로그에 남기지 않고 식별자와 content-free error code만 기록

## 12. 구현 및 검증 상태

현재 구현됨:

- `incident_family` JSON Schema와 예제
- Correlator mapping validation
- Terraform Chat/Datadog mapping validation
- family를 포함한 correlation key
- `UNKNOWN/AMBIGUOUS` fail-safe
- `CORRELATED` revision 전용 Invocation gate
- Worker incident family validation
- source/Incident/revision idempotency와 최신 revision 확인

자동 검증:

- Chat-first → Datadog: 같은 Incident revision 1→2, Invocation 1건
- Datadog-first → Chat: 같은 Incident revision 1→2, Invocation 1건
- 단일 Datadog: State 저장, Invocation 0건
- ambiguity: State 저장, Invocation 0건
- 중복과 same-source update: 추가 revision·Invocation 0건
- 환경 불일치: `SOURCE_ENVIRONMENT_MISMATCH`, 자동 병합 0건
- 미등록 incident family: Correlator와 Worker에서 거부
- 계약 예제와 음성 사례 JSON Schema 검증

## 13. 구현 결과와 남은 운영 gate

1~6은 계약, Correlator, Worker와 자동 테스트로 구현됐다. 7의 정책 동작과 8의 승인 gate도
구현됐지만 숫자와 외부 연결은 아직 열지 않았다. `recovery/cooldown/reopen=0`, Shadow mode,
Adapter·Correlator 비활성이 안전 기본값이다.

남은 일은 합성 Shadow 반복 측정을 `docs/measurements.md`에 기록해 세 window를 0보다 큰 값으로
확정하고, 운영자가 `incident_operational_handoff_approved=true`를 승인한 뒤 운영 monitor ID
mapping·Webhook·source/consumer gate를 함께 전환하는 것이다. 실측과 승인은 코드로 대체하지 않는다.

2026-08-25 운영자는 recovery 300초, cooldown 300초, reopen 1800초와 Operational handoff를
승인했다(D-082). 운영 source는 D-072의 READ_PATH composite monitor `21940250`이며,
`COMPOSITE_CONDITION` corroborating evidence로 등록한다. 실제 적용·검증 상태는
`docs/agent-entrypoint.md`를 따른다.

## 14. 2026-08-25 세션 추가 구현 기록

기존 모니터링 시스템과 기존 `@webhook-o2-dify` 알림 경로는 유지한다. 인시던트는
여러 지표를 사후 상관하는 계층이므로, S1 특가 오픈 과부하를 관찰하기 위한 보조
Monitor만 `infra/05-datadog`에 추가했다.

| 지표 | Datadog Monitor | 초기 Warning/Critical | 용도 |
|---|---:|---:|---|
| `o2.chat.propagation` p95 | `22076983` | `800/1500 ms` | 채팅 fanout 전파 지연 |
| `o2.warm.channel_limited_rate` | `22076982` | `0.05/0.10` | 정상 사용자 채널 차단률 |

두 Monitor는 2026-08-25 운영 Datadog에 Terraform으로 생성·검증했다. 초기 임계값은
반복 측정 후 조정할 수 있는 정책값이다. S1 assessment 계약은
`CHAT_PROPAGATION_P95`와 `CHAT_NORMAL_USER_BLOCK_RATE`에 `broadcast_id`를 필수로
요구하지만, 현재 해당 Datadog 시계열에는 방송별 scope가 없다. 따라서 새 Monitor는
현재 Datadog 알림만 생성하고 Incident webhook/Correlator mapping에는 연결하지 않는다.
방송별 `broadcast_id` 입력 경계를 구현한 뒤에만 webhook을 연결한다. 이 경계를 우회해
가짜 방송 ID를 넣거나 단일 지표만으로 Incident를 승격하지 않는다.

구현 커밋은 `5ada28f` (`feat(monitoring): add S1 chat overload monitors`)이며,
브랜치 `feat/incident-webhook-dify`에 push했다. 기존 READ_PATH 운영 handoff와 Dify
history/권한 설정에는 변경이 없다.
