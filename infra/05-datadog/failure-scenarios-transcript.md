# 시나리오 4 — 캐시가 안 먹는데, 원인이 둘이고 신호가 같다


## 증상

MySQL CPU 88%, 주문 응답 p99 200ms → 1.4초.

## 왜 어려운가

1단계는 쉽습니다.

```
시청자        +15%
MySQL QPS   +400%    ← 시청자 증가로는 설명이 안 됩니다
결론: 캐시가 흡수를 못 하고 있다        ✅ 확실
```

2단계가 안 갈립니다. 캐시가 안 먹는 이유가 둘인데 **같은 그래프를 그립니다**.

| | (a) 무효화 폭주 | (b) 신규 유입 콜드 미스 |
|---|---|---|
| 무슨 일 | 상품 정보가 계속 바뀌어 캐시가 계속 지워짐 | 새로 들어온 사람이 많아 처음부터 캐시에 없음 |
| 캐시 히트율 | 급락 | 급락 |
| MySQL QPS | 폭증 | 폭증 |

## 판별 — 갈리지 않습니다

관측되는 신호는 이렇습니다. **둘 다 조금씩 움직입니다.**

| 신호 | (a) 무효화 폭주 | (b) 콜드 미스 |
|---|---|---|
| 로컬 캐시 히트율 | 급락 | 급락 |
| Valkey 히트율 | 급락 | 급락 |
| 무효화 발행량 | **평소의 3배** | 평소와 같음 |
| 신규 진입 | 평소와 같음 | **+15%** |

무효화도 늘었고 신규 진입도 늘었습니다. 어느 쪽 증가폭도 관측된 QPS 폭증을 **단독으로 설명하지 못합니다.**

**에이전트가 가진 데이터만으로는 못 가릅니다.** "외부 커뮤니티에 링크가 퍼졌다"는 시스템 밖 사건이기 때문입니다. 이것이 이 시나리오가 존재하는 이유입니다.

## 조치가 갈리는 지점

| 오진 | 결과 |
|---|---|
| (b)인데 (a)로 — TTL 상향·무효화 억제 | 낡은 가격이 오래 남습니다. 미스는 그대로 |
| (a)인데 (b)로 — 워밍·파드 증설 | 새 파드도 같이 미스를 냅니다. 효과 없음 |
| **정답 (a): TTL 상향 + 무효화 억제** | 즉시 회복 |
| **정답 (b): 워밍 재실행 + 파드 증설** | 30초 내 회복 |

## 안전한 실험으로 가르기

사람에게 묻는 것 외에 **에이전트가 스스로 가를 방법이 하나 있습니다.**

```
로컬 캐시 TTL 을 10초간 1초 → 3초로 올린다

(a) 무효화 폭주면  →  즉시 회복 (무효화보다 TTL 이 오래 버팀)
(b) 콜드 미스면    →  거의 안 변함 (없는 것은 TTL 을 늘려도 없음)
```

**어느 쪽이어도 해롭지 않습니다.** 최대 손해는 가격 반영이 2초 늦는 것입니다.
4절의 "오진해도 안전한 조치를 먼저"에 해당하며, 이 시나리오에서는 그것이 **조치이자 동시에 판별기**가 됩니다.

## 컨펌 화면

```
┌─ 확인 필요 · inc-2026-0816-003 ─────────────────────┐
│ 판단   캐시 흡수 실패 (확신도 높음)                   │
│ 미정   무효화 폭주 (a)  vs  신규 유입 콜드 미스 (b)   │
│                                                     │
│ 근거   히트율 71→34%, 무효화 3배, 신규진입 +15%       │
│ 배제   Valkey 장애 — evicted_keys 0, 연결오류 0       │
│        트래픽 단독 — +15%로 QPS +400% 설명 불가       │
│                                                     │
│ 질문   예정에 없던 유입이 있었습니까?                  │
│                                                     │
│   [있었다 → (b)]   [없었다 → (a)]   [모르겠다 → 실험] │
└─────────────────────────────────────────────────────┘
```

**[모르겠다]가 있어야 합니다.** 사람도 모를 수 있고, 그때 에이전트가 실험 경로로 넘어갑니다. 이 경로가 없으면 컨펌이 막다른 길이 됩니다.

# 시나리오 1 — 지표는 전부 정상인데 고객이 항의한다

**난이도 ★★★★ / 알림으로 절대 안 잡힘**

## 증상

에러율 0%, 응답 시간 정상, 모든 대시보드 초록불.
그런데 일부 시청자만 옛날 가격을 봅니다.

## 왜 어려운가

Valkey Pub/Sub은 **at-most-once**입니다. 구독자가 순간 끊겨 있으면 유실되고 재전송이 없습니다. 특히 스케일아웃으로 새로 뜬 파드는 이전 무효화 메시지를 못 받습니다.

```
파드 1,2,3  →  무효화 받음  →  새 가격
파드 4      →  나중에 떴음  →  옛 가격을 계속 반환
```

4번 파드에 붙은 시청자만 잘못된 가격을 봅니다. 전체의 **25%**입니다. 그런데 에러가 아니라 200 OK입니다.

## 에이전트가 교차해야 할 것

| 신호 | 무엇을 보나 |
|---|---|
| 파드별 캐시 히트율 | 한 파드만 유독 높다 = 갱신이 안 되고 있다 |
| 파드 생성 시각 vs 무효화 발행 시각 | 파드가 무효화 이후에 떴는지 |
| `product.update` 발행 수 vs 파드별 수신 수 | 차이 나는 파드 특정 |

**"파드 단위로 응답이 갈린다"는 관찰이 핵심입니다.** 사람이 대시보드를 봐서는 거의 못 잡습니다 — 평균으로 뭉개지니까요.

## 조치

해당 파드 재시작 또는 전체 로컬 캐시 플러시. 근본 대응은 재연결 시 전체 플러시(이미 설계에 있음)와 TTL 안전망.

## 주입 방법

```
파드를 하나 스케일아웃한 뒤, 그 직전에 무효화를 발행한다
또는 특정 파드의 Pub/Sub 구독을 끊는다
```

# 시나리오 2 — 특가 오픈 캐스케이드

**난이도 ★★★★★ / 시간축 역추적**

## 증상

특가 오픈 30초 후 전부 느려짐. 채팅 지연, 주문 지연, 영상은 정상.

## 연쇄

```
특가 오픈
  → 발화율 3%/분 → 30%/분          (사람이 흥분함)
  → 팬아웃 80만 → 800만 전달/s
  → chat-gateway CPU 포화
  → WebSocket 끊김
  → 4만 명 동시 재연결
  → 남은 파드도 포화
  → 동시에 주문 2,400 RPS 유입
  → api 가 Valkey 커넥션 대기
  → 주문 응답 지연
  → 사용자가 버튼 연타
  → 요청량 추가 증가
```

## 왜 어려운가

마지막에 관측되는 건 "주문 API가 느리다"입니다. 근본 원인은 채팅 발화율인데, **주문과 채팅은 별개 서비스입니다.**

에이전트가 **시간을 거슬러 올라가야** 합니다.

```
20:14:52   주문 p99 급등              ← 여기서 알림이 옴
20:14:40   api Valkey 대기 증가
20:14:31   WebSocket 재연결 급증
20:14:18   chat-gateway CPU 포화
20:14:06   채팅 인입 20 → 210 msg/s   ← 진짜 시작점
20:14:00   특가 오픈
```

## 조치가 갈리는 지점

| 오진 | 결과 |
|---|---|
| "주문 API 부족" → api 스케일아웃 | 채팅이 여전히 CPU를 먹어 효과 없음 |
| "Valkey 부족" → 노드 등급 상향 | 몇 분 걸리고 원인 아님 |
| **정답: 채팅 표시 상한 하향** | 팬아웃 즉시 감소, 연쇄가 풀림 |

## 주입 방법

```
k6 시나리오에서 특정 시각에 채팅 발화율만 10배로 올린다
주문 부하는 계획대로 유지한다
```

# 시나리오 6 — 주문이 접수는 되는데 확정이 안 된다

2번(캐스케이드)과 같은 **다계층 장애**입니다. 그런데 **스스로 악화되지 않습니다.**
이 차이가 전부입니다.

## 무슨 일이 벌어지나

```
[1] 프론트      "구매 완료!" 화면            정상
[2] API         200 OK, 응답 시간 정상       지표가 전부 초록
[3] 재고 계층   이미 차감됨                  정상
[4] 큐          1,240건이 밀려 있음          ← 진짜 원인은 여기
[5] 처리 워커   느리거나 멈춤
[6] DB          주문이 기록되지 않음
[7] 고객        "주문 내역에 없어요"          ← 증상은 여기서 나옴
```

증상은 맨 끝에서, 원인은 가운데에서 납니다. 2번과 같은 구조입니다.

## 2번과 결정적으로 다른 점

**되먹임이 없습니다.**

```
2번   A → B → C → A     루프가 돌아 30초마다 두 배로 나빠짐
6번   A → B → C         한 방향. 쌓이기만 하고 가속되지 않음
```

큐는 쌓이기만 합니다. 재고가 이미 차감돼서 판매가 멈추면 유입도 멈추고, 사용자가 재시도해도 중복 방지가 막습니다.

**선형으로 나빠집니다. 그래서 판단하고 물어볼 시간이 있습니다.**

## 왜 에이전트가 필요한가

**알림이 오지 않습니다.** 응답 시간도 에러율도 정상입니다. 접수는 실제로 성공했기 때문입니다.

접수된 건수와 확정된 건수를 **대조해야** 간극이 보입니다. 어느 단일 지표도 이걸 알려주지 않습니다.

## 확인 이유 세 가지가 순서대로 나옵니다

### 1막 — 정보 부족

원인이 셋으로 갈리는데 조치가 다릅니다.

> 큐에 1,240건이 밀려 있습니다. 원인이 셋인데 조치가 반대인 것이 있습니다.
>
> - 처리 워커가 부족하다 → 늘린다
> - 워커가 DB에서 막혀 있다 → **늘리면 더 막힌다**
> - 메시지 자체가 처리 불가라 계속 되돌아온다 → 따로 빼낸다
>
> **워커를 하나만 늘려 20초 보겠습니다.** 부족한 거면 즉시 빠지고,
> DB에 막힌 거면 안 빠집니다. 어느 쪽이어도 해롭지 않습니다.

### 2막 — 자기 교정

늘렸는데 큐가 안 빠집니다.

> 1차 판단이 틀렸습니다. 워커 수를 원복했습니다.
> 재조사 결과 DB 쪽에서 잠금 대기가 쌓여 있습니다.

### 3막 — 내 권한 밖

큐를 뚫는 것은 기술 문제지만, **그동안 벌어진 일은 아닙니다.**

> 큐는 뚫었습니다. 그런데 **재고는 차감됐는데 주문 기록이 없는 건이 1,240건**입니다.
> 이 중 340명은 이미 "구매 완료" 화면을 봤습니다.
>
> - 전부 확정 처리 — 재고가 12개 모자랍니다
> - 340건만 확정하고 나머지 취소 — 형평성 문제
> - 전부 취소하고 재고 복구 — 고객 항의
>
> **제가 고를 수 있는 문제가 아닙니다.** 판단해 주시면 실행하겠습니다.

# 시나리오 5 — 1차 조치가 실패하고, 에이전트가 스스로 되돌린다

앞의 시나리오들은 에이전트가 **맞히는 것**을 봅니다. 이것은 **틀렸을 때 무슨 일이 일어나는가**를 봅니다. 에이전트는 틀립니다. **틀렸을 때의 동작이 설계의 품질입니다.**

## 증상

주문 응답 p99 180ms → 1.2초. 알림이 옵니다.

## 시간 순서

```
T+0     주문 응답 p99 180ms → 1.2초. 알림
T+15    1차 판단: "Valkey 커넥션 풀 고갈"
T+20    조치: 풀 상한 10 → 25 (가역 노브, 자동 실행)
        조치 직전 기준값 기록 — p99 1.20초, 풀 대기 340ms
T+80    확인: p99 1.15초                ← 개선 4%
T+82    실패 판정. 풀 상한 자동 원복 (25 → 10)
T+95    재조사. ReplicaLag 1.8초 발견    ← 진짜 원인, 나중에 등장
T+100   2차 판단 + 승인 요청
```

## 왜 어려운가

**1차 판단이 틀렸지만 합리적이었습니다.**

```
주문 응답 느림 + Valkey 대기 증가  →  커넥션 풀 부족
```

정석적인 1순위이고, 사람도 같은 것을 짚습니다.

**그리고 그 시점에는 옳았습니다.** 첫 조사 시점의 `ReplicaLag` 는 0.3초로 정상 범위였습니다. 배제한 것이 잘못이 아닙니다.

그런데 **상황이 진행 중이었습니다.** 조치하고 확인하는 60초 사이에 1.8초로 올라갔습니다. 첫 조사 시점에는 그 신호가 존재하지 않았습니다.

**한 번의 스냅샷 진단으로는 잡을 수 없는 종류입니다.** 확인 루프가 필요한 이유가 이것입니다.

## 판별

| 신호 | 1차 조사 (T+15) | 2차 조사 (T+95) |
|---|---|---|
| Valkey 풀 대기 | 340ms | 320ms |
| `ReplicaLag` | 0.3초 — 정상 | **1.8초** |
| 주문 p99 | 1.20초 | 1.15초 |

**같은 신호를 두 번 봐야 갈립니다.** 한 번만 보면 1차 판단이 최선입니다.

## 조치가 갈리는 지점

| 오진 | 결과 |
|---|---|
| "풀 고갈" → 풀 상한 상향 | 개선 4%. 게다가 남겨두면 **2차 진단이 오염됨** |
| "일단 파드 증설" | 리플리카 부하가 파드 수만큼 늘어 악화 |
| "그냥 기다린다" | 자연 회복되면 맞지만, 아니면 주문 지연이 계속됨 |
| **정답: 주문 직후 조회를 writer 로 고정** | 즉시 회복. 대신 writer 부하 증가 |

## 실패를 어떻게 판정하나

**조치하기 직전에 기준값을 기록해 둡니다.** 이것이 없으면 자기교정이 불가능합니다.

```
조치 전    p99 1.20초,  풀 대기 340ms
60초 후    p99 1.15초,  풀 대기 320ms
판정       개선 4%. 기준(30% 이상) 미달 → 실패
```

**숫자 기준을 미리 정합니다.** 에이전트가 "좋아진 것 같습니다"라고 판정하게 두지 않습니다.

## 왜 자동으로 원복하나

틀린 조치를 남겨두면 **2차 진단이 오염됩니다.** 풀 상한이 25인 채로 재조사하면 무엇이 원래 상태인지 알 수 없습니다.

**실패한 조치는 다음 조사를 시작하기 전에 반드시 되돌립니다.**

## 2차 판단과 승인 요청

> 1차 가설이 틀렸습니다. 풀 상한을 원복했습니다 (25 → 10).
>
> 재조사 결과 `ReplicaLag` 1.8초입니다 (첫 조사 시점 0.3초 — 그때는 정상이었습니다).
